## まちトーク

**画面を見ずに、歩きながら知識を補って、観光をもっと楽しめる。**

スマートグラスをかけて歩くと、通り道の名所の話を、数秒〜15秒だけ耳元で語る音声ガイドです。画面を見る必要はありません。見ているのは景色だけです。

> デモでは、スマートグラスの代わりに Android スマホを横向きにして首の高さで構え、カメラで前を撮りながら歩いています。

## 1. 解きたい困りごと

歩いていて「あの建物は何だろう」「この橋は古そうだな」と思うことがあります。けれども、わざわざ立ち止まってスマホで調べるほどではないので、その小さな好奇心は毎回そのまま捨てられています。

- 観光で町を訪れた人は、ガイドブックに載っている場所しか知らないまま通り過ぎる
- その町に住む人は、毎日通る道にある歴史を知らないまま暮らしている
- 既存の音声ガイドは、決まったコースを歩き、自分で再生ボタンを押す必要がある

（**案**：観光カテゴリとしての言い方は、チームで決める）

## 2. できること

### A. ランドマーク案内（基本の機能）

名所に近づくと、自動で短い話をします。

- 例：「富山駅は、明治41年にいまの場所で開業しました。…」
- 話す内容は、**人が公式の出典と照らして確かめた原稿**だけです
- 公園のような広い場所（エリア）では、入ったときに一度だけ全体の説明をします

### B. 視界の定期検索（追加の機能）

一定の間隔（はじめは20秒）ごとに、今見ている景色をカメラで1枚撮り、写っているものを調べて教えます。地図に登録していないもの（公園の中の橋や建物など）にも答えられます。

- 自信がないときは話しません
- 年号や数字は読み上げません（AI が間違えやすいため）

### 2つを混ぜて、1本の音声にする

| 優先度 | 話すこと | 話し方 |
| :-- | :-- | :-- |
| 1 | 気象警報（気象庁の発表） | 大きな危険（レベル4以上）は、話の途中でも割り込む |
| 5 | A：名所の話 | 名所に最も近づく直前 |
| 6 | B：今見ているものの話 | 答えが返ってきてすぐ。古くなったら捨てる |

今動いているのは、この表の気象警報・A・B の3つです。天気の変化・交通・今日のイベントも同じ仕組みで混ぜられるように形式だけ用意してあり、まだ読み上げません。

同じ話は2回しません。話と話の間は、少し間を空けます。

## 3. 設計の理由（Own the Why）

### たくさん語ることより、黙るべきときに黙ること

毎日使ってもらうには、うるさくないことがいちばん大切だと考えました。次のようなときは話しません（B はカメラの検索もしません）。

- 横断歩道・信号の手前（渡り終えるまで待つ）
- 乗り物に乗っているとき
- すでに聞いた話
- イヤホンがつながっていない・通話中

黙った理由も、話した理由と一緒に記録し、判断画面で見られるようにしています。

### A では、その場で AI を使わない

名所の話で間違ったことを言わないことを最優先にしました。

- 原稿は事前に Gemini で下書きし、**人が公式の出典と照らして確かめたもの**だけを使う
- 「いつ話すか」は端末の中の決まった計算（位置の予測と距離）で決める。同じ歩き方なら、必ず同じ結果になる
- 話す範囲を富山駅付近の10件に絞ったのも、人が中身を確かめられる量にするため

### B のきっかけは「時間」にする

名所の近くだけで話すと、地図に載っていないものには気づけません。そこで、一定の時間ごとに「今見ているもの」を調べることにしました。ただし、AI を使うのは「何が写っているか」の判定だけで、「調べるか」「話すか」は端末の中の決まった計算で決めます。

### 気象は気象庁の発表をそのまま伝える

自分たちで天気を予想して伝えると、予報業務の許可が必要になります。気象庁の発表の内容を決まった文に入れて読むだけにしています。地震・津波・避難の情報は、スマホの緊急速報に任せます。

### プライバシーを守る

- 正確な位置をスマホの外に出さない。サーバーに送るのは、地図のマス目の番号と、丸めた向きだけ
- カメラの画像は保存しない。調べ終わったらすぐ消す
- 画像を送る前に、スマホの中で人の顔を見つけてぼかす

## 4. 使っている Google の技術と選んだ理由

| 技術 | どこで使うか | 選んだ理由 |
| :-- | :-- | :-- |
| Cloud Run | 名所のデータの配信、画像の検索、警報の確認 | 使われていないときはほぼ費用がかからない |
| Vertex AI（Gemini） | 原稿の下書き、B の画像の判定 | 人の手だけでは広げられない地域にも原稿づくりを広げられる。地図にないものにも答えられる |
| Cloud Scheduler | 警報の確認を1分おきに動かす | サーバーを置かずに定期的に動かせる |
| Firebase Cloud Messaging | 警報をスマホに一斉に届ける | スマホが何度も問い合わせなくてよく、電池が持つ |
| Firestore | 警報の前回の状態 | 複数のサーバーで同じ状態を使える |
| ML Kit | 画像を送る前の顔のぼかし | スマホの中で動くので、顔の写った画像を外に出さない |
| Flutter | スマホのアプリと判断画面 | 同じ判断のプログラムを両方で使える |
| Cloud Run（viewer） | 判断画面（Web 版） | API・警報の仕組みと同じ基盤で公開し、使われないときは止まるので費用がほぼかからない |

## 5. デモ

- 場所：富山県富山市の富山駅付近（富山駅 → ブールバール → 富岩運河環水公園 → 富山県美術館）
- 登録した名所：10件（環水公園・富山駅・ブールバール・富山県美術館・オーバード・ホール・ラバーズ像・YKK AP ARENA・富山城址公園・松川べり・桜橋）。位置は OpenStreetMap の座標
- スマホの画面には、審査員に判断を見せるため、カメラの映像・近くの名所・次の検索までの時間・今の判断とその理由を重ねて表示する
- デプロイURLで体験できること：（**案**：録った歩行の記録を判断画面で再生する。チームで決める）

## 6. これから

- 本物のスマートグラスに差し替える（カメラ・向きのセンサー・スピーカー）
- ほかの地域に広げる（同じ形のデータを地域ごとに足し、Gemini の下書きで原稿づくりを速める）
- よく通る道を覚えて、通勤路では1日に1つだけ新しい話をする
- 声での質問（今はマイクを使っていない）
