# 2. プロダクト概要

**スマートグラスをかけて歩くと**、通り道のランドマークの知識を数秒〜15秒で耳元に語る音声ガイド。
歩いている間、一定間隔（既定20秒）で今見ている景色を位置・向き・画像から調べ、マップにないものも音声で教える。利用者が「調べて」と声をかけたときも、そのとき見ているものを調べる。同じ話は繰り返さない。
観光の語りに、気象警報・交通・当日のイベントを優先度つきで混ぜ、1本の音声として届ける。

* 一言：観光地に行かなくても、いつもの道が観光になる
* 対象：生活圏を歩く住民、町を訪れた人
* 原体験：「知りたいけど、調べるほどではない」小さな好奇心が、調べる手間に負けて毎回捨てられている
* コンセプト
  * 歩いている間は画面を見ない。見ているのは景色だけ
  * たくさん語れることより、黙るべきときに黙れることを優先する
  * 便利さは毎日使ってもらうため、豊かさは使ってよかったと思ってもらうため
* 想定端末：**スマートグラス**（カメラ・スピーカー・頭の向きのセンサー）＋ Android スマホ（処理担当）
* **デモ構成：スマートグラスの代わりに、Android スマホを横持ちにして首の高さで構え、常時撮影する**（9章）
* iOS は対象外（将来展望に回す）
* デモエリア：**富山県富山市の富山駅付近**（富岩運河環水公園・富山駅・富山城など。候補の一覧は `docs/spots.md`、道順はメンバー1が決める）

## 2つの機能の分業

| 機能 | A. ランドマーク案内（基本機能） | B. 視界の定期検索（追加機能） |
| :---- | :---- | :---- |
| 役割 | マップに記録したランドマークの知識を伝える | 今見ているものを位置・向き・画像から判断して伝える（建物全体ではなく、画像中央にある部分や対象を説明する） |
| きっかけ | 位置。ランドマークに近づいたとき | 時間。前回の計測から一定間隔（既定20秒）が経ったとき |
| 情報の出どころ | 自分たちで作ったマップ（DB）の原稿 | DB の候補と照合し、なければ画像認識の結果。エリア（公園など）の中では、エリア名と画像から名前の付いた対象を特定し、Google マップのデータで裏付ける |
| 対象 | マップに記録したものだけ | 視界に写っているもの（マップにないものも） |
| 「するか」の判断 | 端末内の決定論的なアルゴリズム | 端末内の決定論的なアルゴリズム（計測するか・話すか） |
| AI | 実行時は使わない | 「何が写っているか」の判定だけに使う |
| 通信 | 先読みしたデータで動く | 計測のたびに画像1枚と粗い位置・向き |

差別化：既存の音声ガイド（VoiceMap、Autio、radiko audio Guide、Guidude など）は「何を語るか」で競う。
このアプリは、A で「いつ、どれだけ語るか」を設計し、B で「マップに載っていない、今目の前にあるもの」まで拾う。

# 3. 最重要の設計方針

1. **A（ランドマーク案内）は実行時に AI を使わない。** 話すかどうか・いつ話すかは端末内の決定論的なアルゴリズムで決め、原稿は DB のものを読む
2. **Gemini の事前バッチ**：A の原稿の下書きを Gemini で作り、人が確認してから DB に保存する
3. **B（視界の定期検索）のきっかけは時間。** 一定間隔（既定20秒）ごとに、今見ている景色を位置・向き・画像から調べる。計測するかどうかは端末内の決定論的なアルゴリズムで決め、同じ話は繰り返さない。利用者が「調べて」と声をかけたときは、間隔を待たずにその場で一度だけ調べる。建物全体ではなく、画像の中央にある対象（建物の特定の部分、道など）を説明する
4. **判断ごとに理由を記録する。** 「なぜ話したか」「なぜ黙ったか」「なぜ検索したか」をログに残し、画面で説明できるようにする
5. **正確な座標を端末の外に出さない。** A でサーバーに送るのはタイル番号・電停 ID・イベント ID・市町村トピックだけ。B で送るのは、計測のたびに画像1枚・地図タイル番号・丸めた方位（例：10°単位）・端末が先読みデータから選んだ候補ランドマーク ID と、撮影の手がかり（町丁目名・範囲の中にいるランドマークの ID と名前・撮影の日時（分まで）・撮ったきっかけ。11/7 にメンバー1が承認）だけ。位置と向きが前回から変わっていないときは送信自体を行わない
6. **カメラ画像は保存しない。** 検索が終わったら画像をすぐ破棄する（端末でもサーバーでも）。送信前に端末内で人の顔を検出し（ML Kit）、写っている場合は顔をぼかしてから送る
   * 例外（11/7、検証用）：開発者モードで「AI に送った画像を保存する」をオンにしたときだけ、送った画像（顔ぼかし後）を端末の歩行ログの隣（`walk_〇〇_images/`）に残す。既定はオフ。歩行ログを消すと一緒に消える。サーバーには残さない。リポジトリに入れない
   * 例外（11/8、デモの説明用。メンバー1が決定）：デモ動画の歩き（`walk_20261108T044257Z`）で AI に送った画像23枚だけ、判断画面（viewer）で撮った判断と並べて公開する。「わからない」で黙った理由を見せるため。顔は ML Kit のぼかし。取りこぼしの小さい顔があった s_000001・s_000006 は、公開の前にアプリと同じ方式のぼかしを手で足した（画面でそう断る）。画面で「AI に送った画像を公開している」と断る。同じ歩きの動画（アプリの画面の録画。通行人の顔はメンバー1がぼかし、音声は消した）も、再生の位置に合わせて地図の上に出す。置き場所は Cloud Storage の公開バケット `ambient-guide-toyama-2026-viewer-images`（リポジトリ・viewer のイメージには入れない＝締切後も消せる）。11/14 のあとに消す
7. **時刻・数字・警報の文面はテンプレートで作る。** AI に書かせない。B の答えでも、年号・数字は DB の原稿にあるものだけを使い、AI が生成した数字は読み上げない
8. **気象は気象庁の発表をそのまま伝える。** 気象庁の発表値・発表文をテンプレートに入れて読む。自前で天気を予想して伝えない（予報業務許可が必要になるため）
9. **地震・津波・自治体の避難指示は扱わない。** OS の緊急速報メールに任せる
10. **B の計測も文脈ゲート（5章）を通ったときだけ行う。** 乗り物の中・横断歩道の手前・アプリが読み上げている最中・音声出力がないときは計測しない
11. **エリアは手動、中身は B。** 公園などの広い場所は「エリア」として範囲と定型文だけを手動で登録し、入ったときに A が定型文を一度話す。エリアの中にある名前の付いた建物・橋・道などは登録せず、B がエリア名・位置・方位・画像から特定して解説する（6章）

# 4. 配信する情報と優先度

**今動いているのは、優先度1の気象警報、5の A、6の B の3つ。** 2（注意報・天気予報の変化）・3（交通）・4（当日のイベント）は、下の表の設計と形式（schema・タイル応答の項目）だけ用意し、まだ読み上げない（18章）。

| 優先度 | 情報 | きっかけ・取得タイミング | 話すタイミング | 文の作り方 | 音楽 |
| :---- | :---- | :---- | :---- | :---- | :---- |
| 1 | 気象警報（大雨・土砂災害・河川氾濫・暴風・大雪など） | サーバーが1分おきに確認し FCM で一斉配信 | 受信後すぐ。**レベル4以上は割り込む** | テンプレート | 一時停止 |
| 2 | 気象（注意報・天気予報の変化） | 数分〜1時間おき | 変化があったときだけ | 気象庁の発表値をテンプレートに入れる | 音量を下げる |
| 3 | 交通（次の便・遅延） | 時刻表は先読み時、遅延は接近予測時 | 電停に近づく直前 | テンプレート（時刻は端末で計算） | 音量を下げる |
| 4 | 当日のイベント | 一覧は朝か起動時、開催状態は接近予測時に再確認 | 会場に近づく直前。確認できたときだけ | テンプレート | 音量を下げる |
| 5 | A：ランドマーク案内（石碑・建物・通り・地名の由来、エリアの定型文） | 周辺タイルの先読み時 | ランドマークに最も近づく直前。エリアは範囲に入ったとき | 事前に作った原稿をそのまま読む | 音量を下げる |
| 6 | B：視界の定期検索 | 前回の計測から一定間隔が経ち、スキップ条件に当たらないとき | 答えが返ってき次第。撮影から鮮度期限を過ぎたら捨てる | DB の候補に一致すれば A の原稿の短い版、なければ Gemini の短い説明（6章） | 音量を下げる |

ルール

* 割り込むのはレベル4以上の警報だけ。それ以外は今の話が終わってから話す
* B は利用者が求めたものではないので A の後ろに置く。B の答えは撮影から鮮度期限内に話せなければ捨てる
* 交通とイベントは期限付き。期限までに話せなければ捨てる
* **話した履歴は A と B で共有する。** ランドマーク全体の紹介はランドマークの ID で管理し、2回しない。**ランドマーク全体の紹介は A だけが行い、B では話さない**（11/6 夜決定。6章「B の仕様」）
* **画像から見つけた特徴（窓の飾り・入口など）は、全体の紹介とは別の話として扱う。** A で建物全体を話したあとなら、新しい特徴を B で話せる。**全体の紹介（A）より先に、その建物・エリアの部分や中のものを B で話さない**（11/6 夜決定）。同じ部分の同じ内容は、言い方や撮った向きが違っても繰り返さない。区別しづらいときは話さない（6章）
* 話題と話題の間は最低間隔を空ける（B が続けて話し続けないように）

# 5. 判断ロジック（端末内・`app/engine`）

## A：ランドマーク案内

1. 位置の平滑化：位置をカルマンフィルタ（状態 [x, y, vx, vy]、等速モデル）で平滑化し、速度と進行方向を求める
2. 先読み判定：2〜3分先までの予測軌跡から、近づきそうなランドマーク・電停・イベント会場を含むタイルを選び、取得の指示（`FetchTiles`）を出す。取得はアプリが行い、届いたタイル（`TilesLoaded`）をエンジンが保持する
3. 発話判定（`ProximityTrigger`）：数十秒先の最接近点がジオフェンスに入り、話し終える前に通り過ぎない候補を選ぶ。エリア（`kind: area`）は範囲に入ったときに定型文を一度だけ話す（`speak:area_entered`）
4. 文脈ゲート（下表）：話す・待つ・短くする・捨てるを決める
5. 優先度キュー：4章の優先度で並べ、話題の間隔を空ける
6. 読み上げ：端末内 TTS。オーディオフォーカスで音楽の音量を下げ、話し終えたら手放す。「右手に」「正面に」など方向を添える
7. 記録：話した内容と黙った理由をログに残す

## 文脈ゲート（A・B 共通）

文脈ゲートは B の計測にも適用する。B では「話さない」は「計測も送信もしない」を意味する。乗り物の中で計測を止めるのは、費用と電池の節約にもなる。

| 状況 | 判定方法 | A の動作 | B の動作 |
| :---- | :---- | :---- | :---- |
| 早歩き | 速度がその人の普段より速い（デモでは固定のしきい値） | 警報と交通だけ話す | 計測しない |
| ゆっくり歩く | 速度が遅い | ナラティブを増やす | 通常どおり |
| 立ち止まる | Activity Recognition が停止 | 長い版を話す | 次の計測を前倒しできる |
| 乗り物に乗っている | Activity Recognition が乗り物 | ナラティブを止める | 計測しない |
| 横断歩道・信号の手前 | OSM の横断歩道・信号までの距離 | 渡り終えるまで待つ | 計測しない |
| アプリが読み上げ中 | TTS の状態 | 今の話が終わるまで待つ | 計測しない |
| 聞いたことがある話 | 端末内の履歴（A・B 共有） | 話さない | 結果を話さない |
| 通勤路 | よく通る道の記録 | 1日1つだけ新しい話 | 1日の回数を減らす |
| いつもと違う道 | よく通る道の記録と照合 | 語る量を増やす | 通常どおり |
| 音声出力なし・通話中 | オーディオの状態 | 話さない（期限付きは期限まで待つ） | 計測しない |

# 6. B：視界の定期検索

## 流れ

1. **計測判定（端末内・決定論的）**：前回から一定間隔が経ち、文脈ゲートを通り、画質が十分で、前回と同じ場所・向きでないとき計測する
2. **候補の選択（端末内）**：先読み済みのランドマークから、現在地から一定距離内かつ視線の方位の左右一定角度内にあるものを候補として選ぶ
3. **画像の取り出し**：その瞬間のカメラ画像を1枚取り、縮小し、顔をぼかす（対象は画像中央の被写体）
4. **検索（クラウド・Cloud Run 経由で Vertex AI）**：画像・タイル番号・丸めた方位・候補 ID を送り、写っているものを調べる
5. **結果の重複判定（端末内）**：これまでに話した内容（A・B 共有の履歴）と同じなら話さない。全体の紹介は ID、特徴は「どの場所・どの部分・何を伝えたか」で比べる（下の「B の仕様」）
6. **答え**：数秒〜15秒の音声。自信がなければ話さない。歩いて位置が変わっているので「さっき右手に見えた〜」のように過去形・方向付きで話す
7. **破棄**：画像は検索後すぐ破棄。ログには計測した理由・判定結果・自信の度合いだけ残す

## 判定のパラメータ（定数ファイルにまとめる）

* 計測間隔（既定20秒）
* 「同じ場所」の判定距離と方位の差
* 候補を選ぶ距離と視線の左右の角度
* 鮮度期限（撮影から話し始めるまでの上限）
* 1回の歩行での計測回数の上限
* 画質のしきい値（ぶれ・暗さ）
* 自信の度合いのしきい値

## B の仕様（11/6 決定。この章のほかの記述や 4章と食い違うときはこちらを優先）

チームの B の仕様書に合わせた決めごと。数値は 17.5 と engine の定数ファイル。

* **撮るきっかけ**
  * 自動：位置と向きが初めて取れてから20秒後に1枚目、その後は前回の撮影から20秒が目安
  * 立ち止まり：5秒止まり、前回の撮影から10秒以上なら前倒しで撮れる（11/6 夜に30秒から下げた。間隔20秒より短くするため）
  * 「調べて」：案内中に聞き取れたら、間隔や「同じ場所」に関係なく、その場で一度だけ撮る
* **撮らない**（自動でも「調べて」でも）：横断歩道・信号の手前15m以内（地図の横断歩道だけで決める。画像の縞模様での判定は 11/7 夜に外した＝影でも反応したため）、乗り物、1.8m/s を超える早歩き、音声出力なし・通話中・読み上げ中・読み上げ待ちあり、前の話の終わりから間隔が空いていない、15秒以内に A が始まりそう、位置・向きが未取得、画質不足（ぶれ0.5・明るさ0.2）、前の検索の結果待ち。自動のときだけ、前回から20m以内かつ向きの差30°以内も撮らない
* **送るもの**：長辺640px 以下の画像1枚（顔はぼかす）、地図タイル番号、10°単位の方位、候補 ID（150m 以内・左右30°・近い順に最大10件。**話したランドマークも候補に残す**＝同じ対象を別の名前で話さないため）、エリアの中ならエリアの情報、撮影の手がかり `context`（任意。町丁目名・範囲の中にいるランドマーク・撮影の日時・きっかけ。11/7 承認）。正確な座標・マイクの音声・認識結果は送らない。API はランドマークの名前をアプリから届いた文字ではなく DB の名前でプロンプトに入れる
* **話す条件**
  * ランドマーク全体：**B では話さない**（11/6 夜決定。全体の紹介は A が近づいたときに行う。`matched`・`whole` が返ったら見送る＝理由コード `answer:whole_left_to_narrative`）
  * **全体の紹介より先に部分を話さない**（11/6 夜決定）：登録したランドマーク・エリアの部分や中のもの（`matched` の部分、エリアの中の `unlisted`）は、そのランドマーク・エリアの全体の紹介（A）が済んでから話す。済んでいなければ見送る＝理由コード `answer:feature_before_intro`
  * **カメラで調べない区域**（11/7 決定）：登録した区域（円）の中では、自動でも「調べて」でも撮らない（`search_skip:no_camera_zone`）。入ったとき・出たときに決まった文で知らせ、A は続ける。入るのは半径以内、出るのは半径＋15m より外。デモでは環水公園の南側（サンフォルテの北東。半径20m）を仮に指定する（動画に字幕で明示）。データは `cloud/data/manual/zones/`、形は `schema/zone.schema.json`
  * **観光の案内として話す価値があるものだけ話す**（11/7 夜に変更）：名所・文化財・パブリックアートなど案内で紹介されるもの、固有の名前・作者・由来があるもの、その場所ならではのデザインだけ。街の設備や日用品（交通安全の設備・シェアサイクル・照明・ベンチ・点字ブロック・のぼり旗など）や、どこにでもあるもの、見た目をなぞるだけの説明しか言えないものは話さない（API が Gemini に `worth_telling` を答えさせ、false なら `unknown`。迷ったら話さない）
  * **名前**（11/7 夜）：固有名は、看板・銘板の文字で読めるか、形で確かに見分けられる有名な場所のときだけ。近くの場所の名前と一般名をつなげた名前は作らない。登録した場所の名前・別名（`aliases`。古い名前を含む）と同じ名前が返ったら、候補なら登録した場所として扱い、候補でなければ B では話さない（古い名前で話さない。全体は A が紹介する）
  * 画像から見つけた特徴：登録された場所かどうかにかかわらず、自信0.7以上で、**具体的な特徴を1つ言えるとき**だけ話す。名前や由来は確かめられた範囲だけ
  * 「わからない」や伝えられる情報がないときは話さない
* **同じ話を繰り返さない**：全体の紹介は ID で A・B 共有。特徴は「どの場所・どの部分・何を伝えたか」を記録し、言い方や撮った向きが違っても同じ内容なら話さない。同じ建物でも別の特徴なら話せる。登録外で固有名のある対象はエリアの中の名前で、それ以外は名前と前回の撮影場所から100m 以内かで履歴を探し、そのうえで部分と内容を比べる。区別しづらいときは話さない
* **鮮度と優先**：撮影から15秒以内に話し始められるときだけ使う。警報 → A → B の順。B を話すと話題の間隔のせいで直後の A に間に合わないなら、B を見送る（`answer:yield_to_narrative`）
* **応答の部分（`part`。11/6 決定）**：応答に `part`（`whole` 全体／`window` 窓／`entrance` 入口・門／`roof` 屋根／`wall` 壁／`pillar` 柱／`sign` 看板／`statue` 像／`railing` 欄干／`planting` 植え込み／`waterside` 水辺／`other` その他。`unknown` は null）を返す。`matched`・`whole` は説明なしで返し、engine が見送る（B では全体を話さない）。`matched`・`whole` 以外は登録したランドマークの特徴で、説明は**写真に見えていること（形・色・素材・飾り）だけ**（由来・歴史・作者は書かない）。説明が残らなければ API が `matched`・`whole` に戻す。同じ話のかぎは（場所, `part`）。形は `schema/api/visual_search.response.schema.json`

## 誤動作を防ぐルール

* アプリが読み上げている最中や、横断歩道の手前では計測しない。「調べて」と頼まれたときも同じで、撮れなければ理由を画面で知らせて依頼を終える（渡り終えたあとに勝手に撮らない）
* アプリ自身の読み上げ音声は「調べて」の合図として扱わない。一度の「調べて」で撮るのは一回だけ
* 同じ方向を見続けていても、計測間隔が経つまでは計測しない
* 画像がぶれている・暗いときは計測しない

## 検索方法の候補（検討の記録）

| 候補 | 仕組み | 長所 | 短所 |
| :---- | :---- | :---- | :---- |
| ① 候補リストから選ばせる | 画像と候補ランドマーク（名前・短い説明）を Gemini に渡し、「どれが写っているか／どれでもない」を選ばせる。一致すれば A の原稿で答える | 答えの根拠が自分たちのマップにある。埋め込みの事前準備がいらない | マップにないものには答えられない |
| ② 埋め込みで照合 | 画像と説明文を同じ空間に埋め込めるモデル（マルチモーダル埋め込み）で比べる | 呼び出しが安く速い | 街中の写真と説明文の一致精度が低い可能性。テキスト専用の埋め込みモデルでは画像と比べられない |
| ③ Gemini に答えさせる | 画像と粗い位置・方位を Gemini に渡し、何が写っているかと短い説明を返させる | マップにないものにも答えられる | 誤りが混ざる。根拠を示しにくい |
| ④ ③＋検索での裏付け | Google 検索でのグラウンディングを付ける | 根拠のある答えにできる | 遅くなる。1回あたりの費用が高い |

当面の方針案：**①と③を1回の Gemini 呼び出しにまとめる**。構造化出力（JSON）で「候補 ID／候補外の対象名と短い説明／わからない」と自信の度合いを返させる。候補 ID が返れば A の原稿で答え、候補外なら自信が高いときだけ短い説明を話す。
いずれの場合も、答えに自信がないときは推測で語らない。動作確認の段階から Gemini の軽量モデル（Flash 系）を Vertex AI で使う（Gemma をセルフデプロイすると GPU の待機費用で予算を超えるため）。

## エリアの中での B（例：富岩運河環水公園）

公園のような広い場所は、園内の建物・橋・道を1つずつ登録しない。エリアとして範囲と定型文だけを登録し、中にある名前の付いた対象は B に任せる。

| 部分 | 例 | 誰が・どうやって |
| :---- | :---- | :---- |
| エリアそのもの | 公園全体の説明 | 手動で登録（`kind: area`、範囲、定型文）。入ったときに A が一度だけ話す |
| エリアの中の名前付きの対象 | 公園内の橋・建物・広場・遊歩道 | 登録しない。B がエリア名・タイル番号・方位・画像から特定し、解説する |

流れ：

1. 端末がエリアの範囲に入ったと判定したら、A がエリアの定型文を話す（正確な位置は外に出さない）
2. エリアの中にいる間の B の問い合わせには、エリアの ID・名前・短い説明を付けて送る
3. Gemini には「利用者はこのエリアの中にいる。画像中央にある、名前の付いた建物・橋・道などを特定し、名前と短い解説を返す」よう頼む
4. ~~名前の裏付けに Vertex AI の Google マップでのグラウンディングを使う（試す方針）。~~ **→ 11/5 に試し、使わないと決めた（15章）。名前の確からしさは、プロンプトの決まり（見分けられるときだけ固有名）と自信の度合いで守る。** 以下は試す前の案： 答えには出典（場所のデータ）を付けて返し、ログと判断画面で「なぜその名前と言ったか」を示せるようにする
5. 固有名が特定できたら `named: true` と名前・解説（目安100字以内、約15秒）を返す。特定できなければ一般名で短く説明するか、自信が低ければ話さない
6. 重複判定は、エリアごとに対象の名前で探し、そのうえで部分と話の内容を比べる（同じ橋の同じ話を2回しない。下の「B の仕様」）

裏付けについての決めごと：

* グラウンディングは**設定1つで外せる**ようにする（`GEMINI_GROUNDING=maps|off`）。画像と一緒に使えない、遅くて鮮度期限に間に合わない、費用が予算に合わない、のどれかに当たれば `off` にして Gemini の判断だけで動かす
* 裏付けがあっても、年号・数字は読み上げない（3章7）

**名前だけのヒントは今は使わない。** エリアに園内の対象の名前だけを並べておく仕組み（`name_hints`）は形式だけ用意してあるが、登録しない。
**予備の手：デモ撮影の試し歩きで、B が名前を取り違える・特定できない失敗が続いたら、メンバー4がそのエリアに名前だけのヒント（出典つき）を登録し、メンバー1が B の問い合わせに含めるよう切り替える。** 判断はメンバー1が行う。

## 自前の地図（デモ用の独自マップ）

Google マップなど既存の地図の施設データをそのまま使うのではなく、**デモの範囲（富山市内のデモルートの周辺）だけに絞った自分たちの地図**を事前に作り、そこに語る対象を記録しておく。

| 入れるもの | 入手先 | 作る人 |
| :---- | :---- | :---- |
| ランドマーク（石碑・建物・通り・地名の由来など。原稿つき） | 自治体のオープンデータ・国土地理院・現地確認をもとに手作業、原稿は Gemini の下書き→人が確認 | メンバー4 |
| エリア（公園など。範囲と定型文だけ） | 同上 | メンバー4 |
| 電停と時刻表、当日のイベント | 公式の時刻表・手作りのモック | メンバー4 |
| 横断歩道・信号 | OpenStreetMap から抽出 | メンバー1（スクリプト） |

* 置き場所：`cloud/data/manual/`（Git 管理）→ SQLite → Cloud Run の API がタイル単位で配る
* **ランドマークの範囲は実際の形で決める（11/7）**：公園は OpenStreetMap の輪郭の中、建物・橋は輪郭から、通り・川は線から決めた幅（`margin_m`）以内（`shape`）。形の無いもの（像など）は中心からの円（`radius_m`）。デモで環水公園の円の範囲が実際の公園とずれ、中で変な動きになったため
* 範囲を絞る理由：語る内容を人が確認できる量に抑えるため（誤った情報を話さないことを優先する）。範囲の外では A は何も話さない
* Google Places API で周辺の施設を取得して蓄える方法は採らない。既存の地図（Google マップ）は使わない。判断画面の地図も、この自前の地図で描く（11/6 決定。15章）。ランドマークの位置は OpenStreetMap の座標で登録する（Google マップの座標は利用規約で保存が制限されているため）
* 将来ほかの地域に広げるときは、同じ形式のデータを地域ごとに足し、Gemini の下書きで原稿づくりを速める

# 9. スマートグラスの想定とデモ構成

## 想定する使い方

利用者はカメラ付きのスマートグラスをかけて歩く。処理はポケットのスマホで行い、音声はグラスのスピーカーから流す。
頭の向きが分かるので、「今見ているもの」を調べられる。

## デモ構成（確定）

スマートグラスはデモまでに用意できないため、Android スマホを横持ちにして首の高さで構え、常時撮影することで代用する。

* スマホの向き＝視線の向きとみなし、端末の方位センサーを視線として使う
* 音声はスマホにつないだイヤホンで聞く
* 画面にはグラス視点の表示（7章）を出し、審査員に判断を見せる
* デモ動画・ピッチでは「スマートグラスの代わりにスマホで撮影している」と必ず明示する
* **デモ撮影のワンタップ（11/7 決定）**：撮影中に本物の警報はまず出ず、案内が割り込まれる場面も起きにくいので、アプリの開発者モードから「ランドマークの案内」「デモの警報（レベル4）」「案内の途中に警報」を押して15秒後に流せる（操作画面を動画から切るため）。本物と同じ入口（警報は受信の入口、案内は engine の `DemoLandmarkRequested`）を通るので、割り込み・順番待ち・記録は本物と同じ。判断画面とログでは「デモ」と分かるようにする（警報の ID は `demo_` で始まる、案内は `speak:demo_landmark`）。動画でも字幕で「デモのため操作して流した」と明示する
* 撮影時の安全：撮影役と歩く役を分けるか、人通りの少ない歩道で行い、横断歩道では立ち止まる。通行人の顔が映った場合は動画でぼかす

実装方針

* `app/engine` は **Flutter に依存しない純粋な Dart パッケージ**にする。通信・読み上げ・撮影・時計の読み取りはしない。入力はイベント（センサー・タイル到着・読み上げ終了・B の結果・警報）、出力はアプリへの指示（話す・タイル取得・撮影して検索・判断ログ）と理由。型は 17.3
* `CameraSource`・`GazeSource`・`TileSource`・検索（`VisualSearch`）は **`app/mobile` 側**のインターフェースにして差し替えられるようにする。テスト用にスタブを用意する
* 歩行ログ（位置・視線・行動）を再生するテストで検証する（スマホなしで動かせること）
* `mobile` と `viewer` は `pubspec.yaml` の `path` 指定で `engine` を参照する
* API と歩行ログのデータ形式は `schema/` の JSON Schema で定義し、Dart と Python の両方がそれに合わせる
* 地図アプリの仕組みを流用する：`z/x/y` タイル単位で先読み・キャッシュ、SQLite の R*Tree で近傍検索、OSM 道路へのマップマッチングで進行方向を安定させる

# 14. コーディング上の約束

* A の判断ロジックに乱数や AI を入れない。同じログ（位置・視線・行動）を入れたら必ず同じ結果になること
* B の「計測するか」「話すか」の判定も決定論的に行う。AI を使うのは「何が写っているか」の判定だけ
* 判断には必ず理由コードを付けてログに出す。例：
  * A：`speak:closest_approach`、`skip:crossing_ahead`、`skip:already_told`、`skip:in_vehicle`
  * B：`search:interval_elapsed`、`search_skip:interval_not_elapsed`、`search_skip:same_place`、`search_skip:low_quality`、文脈ゲートは理由ごと（`search_skip:tts_speaking`・`interval_restarted`・`topic_interval`・`crossing_ahead`・`narrative_soon`・`waiting_turn`・`moving_or_no_audio`。11/7 夜に `search_skip:gate_blocked` から分けた）
  * B の答え：`answer:matched_landmark`、`answer:unlisted_object`、`answer:unknown`、`answer:expired`
* 設定値（ジオフェンス半径、予測時間、計測間隔、候補の距離と角度、ぶれの許容範囲、鮮度期限、検索回数の上限、自信のしきい値、話題の間隔など）は定数ファイルにまとめる
* 外部 API への依存は Repository / Source のインターフェースで抽象化する（例：警報の入口 `JmaPublicFeedSource` を将来 `JmbscPushSource` に差し替えられるように）
* カメラ画像をファイルやログに保存しない（例外は3章6の開発者モードの検証用と、デモの説明用に公開する23枚・歩いた動画だけ）。秘密情報をコードやログに出力しない
* 使ったデータ・ライブラリの出典とライセンスを `docs/attribution.md` に追記していく（著作物利用シート用）

# 17. 部品のつなぎ方（契約）

## 17.1 形式は `schema/` にある

`schema/` に形式（現在 0.3）と見本データ、検証スクリプト（`schema/validate.py`）がある。**各自のテストは `schema/examples/` の見本を読んで通す。** 見本が通れば、相手の本物とつないでも形式で壊れない。

共通の決まり：

* 時刻：UTC の UNIX ミリ秒 `t_ms`（交通の発車時刻だけ現地時刻 `HH:MM`）
* 座標：WGS84 の度（`lat`, `lon`）。距離はメートル、速度は m/s
* 方位：真北を 0°、時計回り。B で送る方位は10°単位の整数
* 地図タイル：XYZ 方式の **z16** 固定
* ID：`lm_0001`（ランドマーク）、`st_0001`（電停）、`ev_0001`（イベント）、`cr_0001`（横断歩道）、`s_000001`（B の検索）、`u_000001`（読み上げ）
* ログは JSON Lines。すべての JSON に `schema_version`

## 17.2 歩行ログ＝エンジンへの入力イベントのログ

歩行ログは**センサーの値だけでなく、エンジンに渡した入力イベントすべて**を1行ずつ記録する（`schema/eventlog.schema.json`）。こうすると、実機で起きたことを机の上（テスト）でも viewer でも、まったく同じに再現できる。

| `type` | いつ記録するか | `data` |
| :---- | :---- | :---- |
| `sensor` | 1秒ごと | 位置・速度・方位・視線・行動・オーディオ状態・画質 |
| `tiles_loaded` | タイルの応答が届いたとき | タイル応答そのもの |
| `tts_finished` | 読み上げが終わったとき | `utterance_id` |
| `visual_result` | B の応答が届いたとき | B の応答そのもの |
| `visual_error` | B が失敗したとき | `search_id`、`error` |
| `alert` | FCM で警報を受けたとき | 警報の ID・レベル・文 |

画像は記録しない。

## 17.3 エンジンの入口と出口

エンジンは**通信・読み上げ・撮影・時計の読み取りをしない**。入力イベントを受けて「やってほしいこと（Command）」を返すだけにする。11章の `CameraSource`・`GazeSource`・`VisualSearch` などのインターフェースは **mobile 側**に置く。

`app/engine/lib/engine.dart` から、次の名前と項目で公開している。

```dart
// ---- 入力（mobile → engine）----
sealed class EngineEvent { int get tMs; }

final class SensorFrame implements EngineEvent {
  final int tMs;
  final double lat, lon, accM;
  final double? speedMps, courseDeg;
  final double gazeAzDeg, gazePitchDeg;
  final Activity activity;          // walking / still / inVehicle / unknown
  final AudioOut audioOut;          // earphone / speaker / none
  final bool inCall, ttsSpeaking;
  final ImageQuality? imageQuality; // blur, brightness（0〜1）
}
final class TilesLoaded implements EngineEvent { final int tMs; final TileResponse tile; }
final class TtsFinished implements EngineEvent { final int tMs; final String utteranceId; }
final class VisualResult implements EngineEvent { final int tMs; final VisualSearchResponse response; }
final class VisualError implements EngineEvent { final int tMs; final String searchId; final String error; }
final class AlertReceived implements EngineEvent {
  final int tMs; final String alertId; final int level; final String kind, areaName, text;
}

// ---- 出力（engine → mobile）----
sealed class Command {}
final class Speak implements Command {
  final String utteranceId, text;
  final int priority;      // 4章の 1〜6
  final bool interrupt;    // true なら今の読み上げを止めて話す（警報レベル4以上だけ）
  final bool pauseMusic;   // true なら音楽を一時停止、false なら音量を下げる
}
final class FetchTiles implements Command { final List<TileId> tiles; }
final class CaptureAndSearch implements Command {
  final String searchId; final TileId tile; final int gazeAzDeg10; final List<String> candidateIds;
  final AreaContext? area;  // エリアの中にいるときだけ（id・name・summary）。B の送信の area にそのまま入れる
}
final class LogDecision implements Command { final Decision decision; }

// ---- 本体 ----
class Engine {
  Engine({EngineConfig config = const EngineConfig()});
  List<Command> handle(EngineEvent event);
}

// ---- JSON との変換（mobile・viewer もこれを使う。各自で別のモデルを作らない）----
EngineEvent eventFromJson(Map<String, dynamic> json);   // eventlog 1行 → イベント
Map<String, dynamic> eventToJson(EngineEvent event);    // イベント → eventlog 1行
// TileResponse・VisualSearchResponse・Decision にも fromJson / toJson を付ける
```

決まり：

* エンジンの時間は**イベントの `tMs` だけで進む**。`sensor` が1秒ごとに来るので、それが時計の代わりになる
* `utteranceId` と `searchId` はエンジンが発行する（連番）
* mobile は API の JSON を engine の `fromJson` で読む。モデルの定義は engine の1か所だけ
* `Engine` の外から中身（内部の状態）を触らない
* **B の送信 JSON** は mobile で組まず、engine の `visualSearchRequestToJson(CaptureAndSearch cmd, String imageJpegBase64)` で作る（形は `schema/api/visual_search.request.schema.json`）。画像はログに出さない
* **割り込み（警報レベル4以上）で止めた読み上げにも `TtsFinished` を返す**。途中で止まった話は「話していない」扱いにして、後でもう一度話せるようにする（engine で判断）
* **B の検索は1件ずつ**。engine は前の `CaptureAndSearch` の結果（`VisualResult`）か失敗（`VisualError`）が来るまで次を出さない。mobile も1件ずつ順番に実行する
* **画面に出す「いまの状態」は、engine の読み取り専用の値で渡す**（判断ログには足さない。歩行ログから同じ値が計算できるので決定論のまま）。
  中身：近くの候補（ID・名前・距離・相対方位）、B の次の計測までの秒数、最後の判断と理由コード。
  mobile のグラス視点の画面と viewer の再生画面の両方で使う
  型（メンバー2、11/6）：`handle()` のあとに `engine.view` を読む。

  ```dart
  final class EngineView {
    final int tMs;                       // 最後に受けたセンサーの時刻
    final List<NearbyLandmark> nearby;   // B の候補の距離（150 m）内、近い順に最大10件
    final AreaContext? currentArea;      // いまいるエリア（既存の型）。外なら null
    final Town? currentTown;             // いまいる町丁目（持っているタイルの代表点でいちばん近いもの。800m より遠ければ null）
    final NoCameraZone? noCameraZone;    // いま中にいるカメラで調べない区域（id・name）。外なら null。中では B を撮らない
    final int? nextSearchInMs;           // B の次の計測まで。結果待ち・上限到達・センサー未着は null
    final String? searchSkipReason;      // B を止めている理由。判断ログの reason と同じ理由コード（例：search_skip:tts_speaking）。止められていなければ null
    final bool searching;                // B の結果を待っている
    final int? searchesLeft;             // この歩行で B をあと何回撮れるか。上限なし（既定）は null
    final Decision? lastDecision;        // 最後の判断（理由コードつき・既存の型）。まだなければ null
  }
  final class NearbyLandmark {
    final String id, name, kind;
    final double distanceM;              // 平滑化した現在地から
    final double relativeBearingDeg;     // 視線から見た方位。右が正、左が負（-180より大きく180以下）
    final bool told;                     // A・B のどちらかで話した
  }
  ```

## 17.4 API

| 項目 | 決まり |
| :---- | :---- |
| A | `GET /v1/tiles/16/{x}/{y}` → `schema/api/tile.response.schema.json` |
| B | `POST /v1/visual-search` → 送受信は `schema/api/visual_search.*.schema.json` |
| 生存確認 | `GET /health` → `{"status":"ok"}` |
| エラー | HTTP 4xx/5xx と `{"error": "<短いコード>"}`。B の失敗は mobile が `visual_error` に変えてエンジンへ |
| エリアと裏付け | B の送信の `area` はエリアの中だけ付ける。応答の `named`・`sources` を engine が使う。裏付けは `settings.py` の `GEMINI_GROUNDING=maps\|off`（6章「エリアの中での B」） |
| 認証 | 当面は `X-App-Token` ヘッダー（値は Secret Manager／`.env`。コミットしない）。App Check への切り替えは将来の課題 |
| タイムアウト | mobile 側で A は5秒、B は8秒 |
| 地域 | Cloud Run・Firestore は `asia-northeast1`（東京）。Vertex AI の地域とモデル名は `cloud/api/app/settings.py`（15章） |

mobile の切り替え：`--dart-define=API_MODE=fake|real`、`--dart-define=API_BASE_URL=...`、`--dart-define=APP_TOKEN=...`。

## 17.6 形式を変えるとき

`schema/` の持ち主（メンバー1）が `schema/`・見本データを直し、`validate.py` が通ることを確かめ、`schema_version` を上げてから全員に知らせる。A の MVP を通った後は項目の追加だけにした（名前の変更・削除はしない）。

# 18. 今回作らないもの（デモの範囲外）

設計（2〜10章）にあるが、デモの範囲外として作らなかったもの。

* 通勤路・よく通る道・いつもと違う道の判定（5章の表の該当行）
* その人の普段の速さを学ぶ処理（早歩きは固定のしきい値）
* 遅延情報（GTFS-RT）の取得、本物の GTFS の取り込み（時刻表は手作りの JSON）
* **交通（電停の時刻表と、その読み上げ）は枠組みだけ**：schema（`stop`・`timetable_file`）、タイル応答の `stops`、SQLite、API は用意済み。時刻表のデータ（`manual/timetable.json`）と engine の交通の読み上げは、デモ完成の後に余裕があれば（データが無ければ `stops` は空で返り、何も話さない）
* 天気予報の変化の読み上げ（4章の優先度2）
* イベント一覧のオープンデータ取り込み（手作りの JSON）
* B の埋め込み照合・Google 検索でのグラウンディング（Google マップでのグラウンディングは試したが使わない。15章）
* エリアの名前だけのヒント（`name_hints`）の登録と送信。形式だけあり、今は使わない。デモ撮影の試し歩きで失敗が続いたときだけ、切り替える（6章）
* iOS、画面オフ・ポケット内での動作、声での質問（マイクは「調べて」の聞き取りだけに使う。7章）
* 本番向けの DB（Cloud SQL・Spanner）
